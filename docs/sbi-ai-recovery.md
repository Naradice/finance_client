# SBI画面変更へのAI追従（参照・Selenium操作）

`STOCK` と `StatefulScreening` のSelenium要素検索を共通の復旧処理に接続しています。
ログイン・メール認証・画面移動・銘柄検索・注文フォーム・売却・取消・スクリーニングを対象にします。
通常は既存のSelenium処理を実行し、対象要素が見つからない場合だけAIに変更後の位置を提案させます。
買付余力・保有銘柄・注文一覧には、表の項目と取得結果を検証する専用の復旧処理もあります。
非公開APIの呼び出しや通信の解析は行いません。

## 普段のChromeを使用する

`.env` の `SBI_CHROME_DEBUGGER_ADDRESS=auto` で、起動済みの普段のChromeへ接続します。
Chrome 144以降の `chrome://inspect/#remote-debugging` で接続を有効にし、Chromeが表示する接続許可を承認してください。
この方式ではChromeの仕様により接続のたびに許可ダイアログが出ます。一度だけ許可する設定ではありません。
許可式接続が従来のHTTP検出に対応しない場合は、同じPCのループバック上で一時的なCDP接続ブリッジを起動し、Seleniumへ接続します。Chrome側の接続許可は引き続き必要です。
既存のChromeを再起動せず、スクリプト用のタブを1つ作成します。終了時は作成したタブとWebDriver接続だけを閉じます。
ChromeDriverにブラウザー全体の終了命令は送信しません。プロファイルのコピーやCookieの取り出しは行いません。
既定の検出先はWindowsの `%LOCALAPPDATA%/Google/Chrome/User Data/DevToolsActivePort` です。
別の保存先の場合は `SBI_CHROME_ATTACH_USER_DATA_DIR`、既知の接続先は `SBI_CHROME_DEBUGGER_ADDRESS=127.0.0.1:ポート` を指定できます。
接続先は同じPCのループバックアドレスに限定します。接続設定が無効な場合に別プロファイルで起動する代替処理は行いません。

この設定を省略すると、従来の固定プロファイルでChromeを起動します。
保存先は `SBI_CHROME_USER_DATA_DIR`、プロファイルは `SBI_CHROME_PROFILE_DIRECTORY`、実行ファイルは `SBI_CHROME_BINARY` で変更できます。
固定プロファイルで起動する方式では、上記の接続許可ダイアログを使用しません。プロファイルは実行後も保持されます。
ただしChrome 136以降では、通常のChromeの標準データ保存先をそのまま指定する起動方法はサポートされません。
別の固定データ保存先を使い、SBIの手動操作にも同じプロファイルを使う構成になります。
参考: [接続ごとの許可](https://developer.chrome.com/blog/chrome-devtools-mcp-debug-your-browser-session)、[Chrome 136以降の保存先制限](https://developer.chrome.com/blog/remote-debugging-port)。
固定していた不完全なChrome 114のUAは廃止し、実際のChromeのUAを使用します。
同じプロファイルを使っても、SBI側の取引時認証が不要になることを保証する設定ではありません。

### 接続許可を毎回求めない固定プロファイル方式

両プロジェクトから同じSBI用プロファイルを利用する場合は、それぞれの `.env` に次の設定を保存します。

```dotenv
SBI_CHROME_DEBUGGER_ADDRESS=
SBI_CHROME_USER_DATA_DIR=C:/path/to/finance_client/src/finance_client/sbi/sbi_util/sbi_util/profile
SBI_CHROME_PROFILE_DIRECTORY=Default
```

`SBI_CHROME_DEBUGGER_ADDRESS` を空にすることで、起動済みの通常のChromeへの接続から、SeleniumによるChrome起動へ切り替わります。
上記は以前からあるSBI用プロファイルの保存先です。ログイン状態やサイトの保存データは同じ場所に残り、毎回新しいプロファイルは作りません。
通常のChromeのタブとは別のウィンドウになり、スクリプト終了時にこのSBI用Chromeを閉じます。
このSBI用Chromeを手動で開いている間は、同じプロファイルを使うスクリプトを同時起動しないでください。

## 有効化

プロジェクトのPython環境で追加依存関係をインストールします。

```powershell
python -m pip install -e '.[sbi-ai]'
```

プロジェクト直下の `.env` に設定します。`.env.example` をコピーして値を記入してください。
既存の `.env` がある場合はコピーで上書きせず、必要な設定を追記してください。
モデルは利用可能なStructured Outputs対応モデルを指定します。
AIへの問い合わせには設定したOpenAI APIの利用料金が発生します。

```dotenv
SBI_AI_HEALING=1
SBI_AI_MODEL=<利用するモデル名>
OPENAI_API_KEY=<APIキー>
sbi_id=<ログインID>
sbi_password=<ログインパスワード>
```

```powershell
python samples/sbi_read_only.py
```

サンプル、`SBIClient`、`STOCK`、`ReadRecovery.from_env()` はプロジェクト直下の `.env` を自動で読み込みます。
実行時の作業フォルダーには依存しません。設定済みの環境変数は `.env` より優先され、
コンストラクターに渡したログイン情報は環境変数より優先されます。
UTF-8（BOM付きも可）を使ってください。値中の `${...}` は置換せずそのまま扱います。
`.env` は既存の `.gitignore` により管理対象外です。
配布パッケージなどでプロジェクトが見つからない場合は、`load_sbi_env("設定ファイルの絶対パス")` で指定できます。

このサンプルは必ず読み取り専用で動作します。取引パスワードは不要です。
ログイン・端末認証の画面操作は、従来の端末登録と、実画面で確認した直接コード入力（`otp` / `submit-otp`）に対応します。
認証画面の入力欄・ボタンにも、後述の共通要素検索の復旧を適用します。
認証メールの形式変更には、以下のメール読み取り処理で対応します。
サンプルは取得結果を標準出力に表示するため、出力にも口座情報が含まれます。

既存コードでは環境変数による有効化に加え、引数でも指定できます。

```python
from finance_client.sbi.client import SBIClient
from finance_client.sbi.sbi_util.sbi_util.read_recovery import ReadRecovery, OpenAIRecipeProposer

recovery = ReadRecovery(
    OpenAIRecipeProposer(model="<利用するモデル名>"),
    cache_dir=".cache/sbi_read",
)
client = SBIClient(read_recovery=recovery, read_only=True, use_yfinance=False)
try:
    budget = client.rpa_client.get_available_budget()
    positions = client.rpa_client.get_positions()
    orders = client.rpa_client.get_orders()
finally:
    client.close_client()
```

`SBI_AI_HEALING` が未設定で `read_recovery` も渡さなければ、従来の処理を使います。
AI追従を有効にして `read_only` を省略した場合は、読み取り専用になります。
`read_only=False` を明示すると売買処理が有効になり、その入力欄・ボタンにも共通の復旧を適用します。
AIが注文数量・価格・銘柄を決めることはありません。実行する操作と入力値は呼び出し元のコードが決めます。
読み取り専用の既定値と、明示した `read_only` 設定は維持しています。

## 全ページ共通のSelenium要素検索

`HealingDriver` / `HealingElement` が `find_element()` / `find_elements()` を扱います。
要素内からの相対検索、Seleniumの待機条件、フレーム内の検索にも同じ仕組みを適用します。
既存の要素を取得できれば通常の処理を続けます。登録済みの入力欄では非表示の旧要素を除外します。
無効状態のボタンも要素として取得し、クリック・入力の直前に有効化を待ちます。
認証コード入力前に確認ボタンが無効な状態でも、画面の判別や取得先の検証は失敗扱いにしません。

- ログインID・パスワード・認証コード・注文数量・価格・取引パスワード・注文送信・取消送信などには、
  最初のアクセスでも変更後のIDを探索できる意味の定義を用意しています。
- その他の検索先は、正常に取得できたときの公開ラベル、要素の種類、周辺・内部の公開ラベルから
  意味の定義をローカル保存します。スクリーニングの条件枠や複数選択項目にも使います。
- 失敗時は現在の画面から意味が一致する候補を抽出し、AIに構造上のXPathだけを提案させます。
  単一要素が曖昧な場合、候補の欠落、別の入力欄への置換、属性条件やコードを含む提案は採用しません。
- AIへ渡すのは登録済みの公開ラベルとタグ・入力の種類・構造パスだけです。
  入力値、認証コード、パスワード、銘柄名・コード、口座情報、URL、HTML属性は送信しません。
- 選択肢の意味が異なる一覧では、正常時に各項目の意味を保存します。新たに追加・変更された項目を
  既存の位置と同じ意味だと推測する機能はありません。項目の並び順に依存する既存処理の制約は残ります。
- SBIのHTTPSページと、現在のフレームの接続先を両方検証します。外部サイトのフレーム、
  外部フォームへの送信、任意の `javascript:` リンクは拒否します。
  SBI既存の「指定フォームのActionID設定→送信」という画像ボタンは、固定した構文と
  参照先フォームのPOST方式・SBIのHTTPS送信先を検証して対応します。リンクのコードを評価・生成しません。

既定で `SBI_AI_HEALING=1` に連動します。共通の要素検索だけ無効にする場合は、
`.env` に `SBI_AI_OPERATION_HEALING=0` を設定してください。
保存先の既定値は `~/.cache/finance_client/sbi_operations` で、`SBI_AI_OPERATION_CACHE_DIR` で変更できます。
保存するのは公開ラベルと構造上のパスだけです。元のURL・検索条件・スコープはハッシュ化します。
構造が同じ場合も、現在の候補との一致・表示状態を再検証してから保存済みの取得先を使います。
失敗した同じ構造への問い合わせは、同じ復旧インスタンス内で繰り返しません。

引数で指定する場合は `SBIClient` / `STOCK` / `StatefulScreening` の `operation_recovery` に
`SeleniumRecovery(proposer, cache_dir)` を渡せます。`False` を渡すと、この層だけ明示的に無効化します。
認証関数を単独で使う場合は `enable_recovery(driver)` を渡してください。

これは要素の位置の修正です。Pythonコードを書き換えたり、AIが操作手順を追加したりはしません。
登録された意味も正常時の記録もない要素、ラベルが未知の用語に変わった場合、画面の意味・取引仕様の変更、
処理が例外を出さず誤った要素を取得してしまう場合には、自動追従を保証しません。
スクリーニングの数値条件や評価集計など、既存の値の解釈処理そのものをAIで置き換える機能はありません。
未実装の操作を実装済みにする機能でもありません。

## 発注・取消の復旧と送信結果

変更後の注文数量、価格、成行選択、取引パスワード、確認省略、注文送信・取消送信の要素を探索します。
注文数量は従来どおり売買単位を掛けた株数です。売買単位を確認できなければ送信しません。
売却・取消の一覧が変わった場合は照会処理でデータを確認し、対象銘柄が一致する行内で操作先を探索します。
同じ銘柄の注文や保有区分が複数ある場合は、最初の1件を推測して選ばず停止します。

クリック・入力の実行後に通信エラーが出た場合、その操作は再実行しません。
古くなった単一要素は実行前に取り直しますが、一覧の要素は行が入れ替わる可能性があるため停止します。
入力欄を探し直すことと、送信済みの注文を再送することを分けています。
共通の復旧を有効にした発注・取消では、明確な受付／取消完了表示、または明示的なエラーを待ちます。
電話による取引時認証はメールOTPと分けて検出します。`STOCK`／`SBIClient` に
`phone_auth_handler`（残り秒数を受け取り、登録電話からの発信後に `True` を返す関数）を渡すと、
認証ボタンを1回だけ押し、元の送信結果の確認に戻ります。電話発信や注文の再送は行いません。
ハンドラーがない場合は `PhoneAuthenticationRequired`、待機の期限切れは `PhoneAuthenticationTimeout`、
認証未完了は `PhoneAuthenticationFailed` として停止し、送信結果が未確定である状態を維持します。
`samples/sbi_order_cycle.py --execute` は、端末のEnterとブラウザー上の手動完了の両方を監視するハンドラーを設定します。
ブラウザーで手動認証を完了した場合は端末のEnterを求めず、認証ボタンを追加で押しません。
認証ボタンをスクリプトが押した後の待機も、短い固定20秒ではなく、最初に設定した期限までの残り時間を使います。
SBI画面の期限切れ表示は途中でも検出して停止します。SBI側の3分の期限自体は延長しません。
送信後の結果が確認できない場合は `ActionOutcomeUnknown` で停止し、同じ `STOCK` インスタンスの
追加発注・取消を止めます。注文状況を確認してから再開してください。
この停止状態はプロセスをまたいで永続化されないため、呼び出し側でも不明な注文の自動再送・自動再起動を避けてください。

旧実装の「発注処理が失敗しても `buy_order()` が成功を返す」挙動を修正しました。
共通復旧を有効にした取消では、クリックできただけでは成功を返しません。

## 取得先の検証

- AIが返せるのは構造だけで指定したXPathのJSONです。コードやJavaScriptを実行させる機能はありません。
- 画面名、各項目の見出し、候補の一意性、数値の形式と範囲を確認します。
- 表では見出しと値の列位置をブラウザー上で照合します。取得単価と現在値を入れ替えた提案は拒否します。
- 保有株数から注文中株数を差し引き、売却可能株数を既存の `holding` に返します。
  注文中株数が不明な場合にゼロと推測することはありません。
- 一覧の取得失敗を空の口座と扱いません。空の一覧には、対応する明示的な「ありません」表示が必要です。
- AI追従を有効にした公開参照メソッドの売買・取消リンクは `None` です。辞書のキーは維持します。
- 再探索からの画面遷移は、固定した参照用のリンク名とHTTPSのSBIリンクに限定します。
  認証画面、外部サイト、`javascript:` リンク、曖昧なリンクでは停止します。

正常な既存の取得処理はこれまでの方法を使い、結果の基本的な型と範囲を追加確認します。
上記の見出し・列位置による厳密な照合は、AI提案と保存済みの取得方法に適用します。

## AIに渡す情報と保存内容

AIへ送る情報は、表示中の画面のタグ階層と、コードに登録した項目名だけです。
数値は `[number]`、銘柄名・氏名など登録項目名以外の文字列は `[text]` に置き換えます。
入力欄、隠し要素、HTML属性、URL、Cookie、スクリプト、画像は送りません。
API呼び出しでは `store=False` を指定します。API側のデータ取扱いは利用するアカウントの設定・条件にも従います。

検証を通った取得先は、ホスト・参照対象別にローカル保存します。画面構造の指紋と取得先だけを保存し、
口座情報は保存しません。構造が一致する次回の取得では、保存先を再検証して読み取り、AI問い合わせを省略します。
初期保存先は `~/.cache/finance_client/sbi_read`、変更する場合は `SBI_AI_CACHE_DIR` を設定します。
破損した保存内容は再探索で置き換えます。

AI提案の取得・検証に失敗した場合は `ReadRecoveryError` を送出します。
診断ファイル `<対象>-failure.json` には対象名と例外の型だけを記録します。
既存Selenium処理には従来の口座情報を含むログ出力が残っているため、通常のログも適切に管理してください。
一度の再探索につきAI問い合わせは最大1回、APIタイムアウトは30秒、SDK自動再試行は無効です。

## 専用データ取得の対応範囲

新しい画面への追従が必ず成功するものではありません。実接続で確認できた範囲と未完了の項目は、
下記「認証メールの形式変更への追従」の動作確認結果を参照してください。

- 買付余力は、明確なラベルの近くに金額が1つだけある構造を扱います。
- 保有銘柄・注文一覧は、各項目の列見出しがある単一のHTML表、または標準のtable/gridロールを持つ構造を扱います。
- 結合セル、複数段の見出し、上下2行で1件を表現する一覧、複数の一覧表、見出しが不明なdivの集合には追従しません。
- ページ送りが表示されている一覧は、途中までのデータを返さず停止します。仮想スクロールの一覧も対象外です。
- 上記の専用データ取得処理とは別に、認証・発注・取消・スクリーニング等の要素検索には共通復旧を適用します。
  訂正操作そのものは既存の公開実行メソッドがないため追加していません。
- スクリーンショットによる探索は含みません。画面構造で検証できる範囲に限定しています。

未対応の構造を見つけた場合は、秘密情報を除いた画面構造を使って専用の検証・取得処理を追加します。
表示されていない行やページ送りを独自に検出できない構造もあるため、実口座での初回確認では
画面上の件数・残高・株数と照合してください。

## 認証メールの形式変更への追従

認証メールはGmail APIの読み取り専用権限で取得します。`.env` に、Gmail OAuth用の設定ファイルと、
取得したトークンの保存先を指定できます。`GOOGLE_API_KEY` や `OPENAI_API_KEY` はGmailの認可には使えません。

```dotenv
SBI_GMAIL_CREDENTIALS_FILE=C:/your-settings/credentials.json
SBI_GMAIL_TOKEN_FILE=C:/your-settings/token.json
# 省略するとSBI_AI_HEALINGと同じ値。メールのAI探索だけ止める場合は0。
SBI_AI_EMAIL_HEALING=1
```

既存の `mail/credentials.json` と `mail/token.json` も引き続き初期設定の保存先として使えます。
初回のGmail OAuth認可ではブラウザーの操作が必要です。OAuth認可がない状態でメールを取得することはできません。
OAuth用Google CloudプロジェクトでGmail APIも有効にしてください。認可済みでも未有効の場合は
`403 accessNotConfigured` になります。[Google公式セットアップ](https://developers.google.com/workspace/gmail/api/quickstart/python)

1. 固定件名への依存を外し、`info@sbisec.co.jp` から最近届いたメールを検索します。
   送信元を取得後にも照合し、Google受信側の `Authentication-Results` にあるDMARC成功とSBIドメインを確認します。
   ログイン時はメール送信要求より前のメールを除外します。受信時刻が秒単位で返るため、要求時刻も秒単位で比較します。
   要求時刻を指定しない端末認証コードの取得は原則直近1分を対象とします。
2. 入れ子のMIME、HTMLのみのメール、文字コード指定、HTMLリンクを読み取ります。
   添付ファイル、スクリプト、非表示の本文は抽出対象から外します。
3. 認証を示すラベルに近いコード・URL候補をローカルで抽出します。口座番号、電話番号、期限などの候補を除外し、
   従来形式で一意に判別できる場合はAIを呼びません。
4. 形式が変わった場合は、候補の種類・長さ・周辺の既知の項目名だけをAIに渡して候補番号を選ばせます。
   本文全文、氏名、メールアドレス、コード、URL、トークンは渡しません。
5. 候補が実際に存在し、認証用途の文脈と一致することを再検証します。URLはHTTPSのSBIドメインに限定し、
   認証画面を開いた後の遷移先も検証します。成功した候補番号と匿名化した構造の指紋を保存し、次回は再利用します。

候補番号を選ぶ仕組みなので、AIがコードやURLを作ることはできません。
英数字コードは4〜12文字で数字を含む形式を対象とします。新しい用語で認証用途を確認できない場合、
送信元・メール認証方式が変わった場合、URLが外部に移転した場合などは自動採用せず停止します。
DMARC結果が得られない転送メールも対象外です。任意のメール形式変更への追従を保証するものではありません。

コードやURLをログに出力していた旧処理は削除しました。コードが拒否された場合に同じメールを無限に再試行する
処理も停止します。HTMLの装飾による大量の改行・空白を正規化し、認証ラベルとコードの対応を確認します。

2026-10-23の実接続確認では、Gmail APIの認可・メール取得、新形式のHTMLメールからのコード抽出、
SBIのコード直接入力による自動ログイン、買付余力と保有銘柄の取得が成功しました。

実注文が存在する一覧のAI修復は、ローカルの模擬画面での確認までです。
